\begin{abstract}
Smart contracts written for low-resource blockchain ecosystems, such as Algorand's PyTeal and
Solana's Rust, are poorly served by mainstream static-analysis tooling and are underrepresented in
LLM pre-training datasets, leading to hallucinated findings and missed detections under zero-shot
prompting. This paper proposes and evaluates a hybrid, LLM-centric vulnerability-detection pipeline
combining Retrieval-Augmented Generation (RAG) over an LLM-generated, semantic-description knowledge
base with Chain-of-Thought supervised fine-tuning of medium-scale open-weight models, evaluated on
both ecosystems across four open-weight model families (Qwen3-32B, QwQ-32B, Gemma-4-31B,
Qwen3-Coder-30B-A3B) and a SOTA generalist benchmark (DeepSeek-V4-Pro). RAG raises F1 in every one
of the sixteen open-weight configurations tested; fine-tuning's incremental contribution on top of
it is model-dependent, measurable for Qwen3-32B and QwQ-32B but statistically null for Gemma-4-31B
and Qwen3-Coder-30B-A3B on at least one language each. On 45 held-out Algorand contracts, the best
configuration per model raises F1 from 0.45 to 0.80--0.95, statistically indistinguishable from the
SOTA generalist (F1 0.918) while remaining deployable on-premise; on 97 held-out Solana contracts,
the same configuration raises F1 from 0.33 to 0.57--0.63 for Qwen3-32B and QwQ-32B, at lower absolute
performance than Algorand but the same ordering. This pattern is not universal: Gemma-4-31B closes
the Algorand gap to the SOTA generalist from RAG alone, and on Solana both Gemma-4-31B and the
sparse mixture-of-experts Qwen3-Coder-30B-A3B show the same null fine-tuning contribution once RAG
is present, whether fine-tuning adds value on top of retrieval is governed by which specific model
is being adapted, not by parameter scale alone.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Blockchain technology has redefined digital trust by enabling the decentralized execution of 
programmable agreements, or smart contracts, without intermediaries. Among post-Ethereum platforms, 
Algorand and Solana both pursue high throughput and low latency through consensus and runtime
designs quite
different from Ethereum's, via a Pure Proof-of-Stake (PPoS) protocol for the first, and with a
Proof-of-History-ordered, parallel-execution (Sealevel) runtime for the latter.
Neither design prevents the central security constraint of the smart-contract paradigm: once
deployed, contract code is effectively immutable, so any residual vulnerability is permanent 
and can lead to irreversible financial loss.

Algorand contracts are written in PyTeal, a Python DSL 
compiling to TEAL bytecode. Solana programs, instead, are typically 
written in Rust, compiled to SBF bytecode: every account passed 
into an instruction is an untyped, attacker-suppliable reference, so omitting an ownership, 
signer, type, or CPI-target check yields an exploitable vulnerability with no counterpart 
in account-model chains like Ethereum. Two dominant auditing approaches well-known in Ethereum
blockchain security fall short on both stacks: static-analysis tools (Slither
\cite{feist2019slither},
SmartCheck \cite{tikhomirov2018smartcheck}) are built 
for the EVM and cannot port to these execution models, while rule-based analysis 
struggles with contract-specific business logic; general-purpose LLMs degrade sharply on 
these low-resource languages, hallucinating non-existent syntax or overlooking 
platform-specific primitives (transaction rekeying, non-canonical bump seeds) absent from EVM-based
chains.
Our earlier taxonomic study \cite{boi2025} on prompt engineering versus fine-tuning 
for LLM-based vulnerability detection on Algorand and Solana, established that 
PyTeal is markedly harder for LLMs to reason about than Rust and that 
fine-tuning is necessary to move base models beyond a null F1-score 
on several vulnerability classes. Building on that finding, we ask two research 
questions that the earlier study left open:

\begin{itemize}
    \item \textbf{RQ1.} Is inference-time retrieval of vulnerability-specific context
    (Retrieval-Augmented Generation) sufficient on its own to close the domain gap,
    or does supervised Chain-of-Thought fine-tuning add further, measurable value on top of it?
    \item \textbf{RQ2.} Does the answer to RQ1 depend on model scale, i.e., do
     medium-scale open-weight models (on the order of 32B parameters) and massive 
     generalist models (on the order of $10^{2}$--$10^{3}$B parameters) benefit differently 
     from fine-tuning and retrieval?
\end{itemize}

To answer these questions we design, implement,
and evaluate a hybrid, LLM-centric vulnerability-detection pipeline, instantiated independently
for Algorand and for Solana, that combines two adaptation strategies. First, we implement a RAG
module, with separated knowledge base per language, that retrieves the snippets and security
checklists most relevant to the contract under analysis; to avoid conflating functional similarity
with security similarity, retrieval is performed over LLM-generated, syntax-agnostic security
descriptions of contract logic. Second, for each blockchain's programming language we construct a
curated instruction-tuning dataset in which every training response is decomposed into an explicit
reasoning trace (Chain-of-Thought, CoT) followed by a structured verdict, and use it to fine-tune
32B reasoning-oriented open-weight models (Qwen3-32B for both languages, and additionally QwQ-32B
for Algorand) via quantized low-rank adaptation (QLoRA). Both components are evaluated in isolation
and in combination on each language independently.

The contributions of this paper are as follows:
\begin{enumerate}
    \item Two reusable vulnerability knowledge bases and dataset-construction 
    methodologies with eight OWASP-mapped classes for Algorand and seven for Solana, 
    together with a multi-task instruction-tuning schema (vulnerability detection, 
targeted vulnerability verification, semantic code description) tailored to a RAG-compatible
pipeline.
    \item A semantic-abstraction RAG design that mitigates the well-known raw-code
    retrieval bias by indexing natural-language security descriptions, coupled with a
diversification strategy and a similarity-ranked dynamic checklist injected into the audit prompt.
    %This is the pipeline's most consistently effective component: it raises F1 in every one of the
    %sixteen open-weight configurations evaluated (Section~\ref{sec:results_overall}).
    \item A Chain-of-Thought fine-tuning architecture for 32B reasoning models, applied to both
    languages and validated through learning-curve analysis and early-stopping
    at the empirically identified generalization optimum. 
    Its contribution on top of RAG is
    model-dependent 
    %rather than uniform (Finding 4--6, Section~\ref{sec:cross_arch_results})
    , and a
    dedicated ablation (Section~\ref{sec:cot_ablation}) shows that where 
    it does help, the gain traces
    to the breadth of the multi-task training.
\item A benchmark comparing base and fine-tuned models, with and without RAG, on held-out sets of 45
    Algorand and 97 Solana contracts, plus a cross-language analysis of where the approach's gains 
    generalize and where they do not.
\end{enumerate}

\section{Background and Related Work}
\label{sec:background}

\subsection{The Algorand Virtual Machine and PyTeal}
\label{sec:avm}

Unlike EVM-based chains, Algorand separates consensus from application logic 
through the Algorand Virtual Machine (AVM), a non-Turing-complete, stack-based interpreter 
under Pure Proof-of-Stake consensus. The attack surface is caused by three features Algorand which
are absent from EVM-based chains:
Algorand Standard Assets (ASAs) are protocol-managed primitives (no reentrancy, 
but asset-transfer permission risks with no EVM analogue); a dual state model separates 
global application state from per-account local state, and improper read/write discipline 
across the two is a common error source; and atomic grouping bundles up to 16 transactions 
to succeed or fail together, requiring security analysis across the group rather than in isolation.

Contracts are written in PyTeal, a Python library compiling to TEAL, the bytecode 
executed by the AVM. Because PyTeal is not executed directly on-chain, syntactically correct 
Python can compile into an insecure TEAL program if a check is omitted -- models must 
reason about the compiled semantics of constructs like \texttt{Seq}/\texttt{Cond}/\texttt{Assert},
not
just surface syntax. Algorand further distinguishes stateless contracts (Logic Signatures, 
delegated signature authorities where an unchecked field, e.g.\ \texttt{RekeyTo}, is an 
identity-theft vector) from stateful ones (Applications, where the dominant risk is 
unauthorized state mutation or lifecycle abuse, e.g.\ an unprotected \texttt{DeleteApplication}
branch).

\subsection{The Solana Sealevel Runtime and Rust/Anchor Programs}
\label{sec:sealevel}

Solana orders transactions via Proof-of-History and executes them on \textbf{Sealevel}, a runtime
parallelizing non-overlapping transactions across cores. Programs compile to SBF bytecode and are
typically authored in \textbf{Rust}, often with the \textbf{Anchor} framework. Three features shape
its attack surface with no Algorand counterpart. Solana is \emph{account-centric}: every account a
program reads or writes is a caller-supplied, untyped \texttt{AccountInfo}, and verifying ownership,
type (vs.\ \emph{type confusion}), and signer status (\emph{missing key check}) is entirely the
program's responsibility. Programs routinely delegate work via \emph{Cross-Program Invocation}
(CPI); an unvalidated callee program ID or forwarded account enables substitution (CPI reentrancy /
unchecked external calls). \emph{Program Derived Addresses} require using the \emph{canonical} bump
seed; accepting a non-canonical one lets an attacker derive an unintended account. Integer overflow
and denial-of-service (missing reinitialization guards, unbounded growth) round out the seven-class
taxonomy; several classes require tracing a value across multiple instructions or a CPI boundary,
unlike Algorand's largely single-transaction checks.

\subsection{LLMs, Retrieval-Augmented Generation, and Parameter-Efficient Fine-Tuning}
\label{sec:llm_background}

Modern LLMs are autoregressive Transformer decoders \cite{vaswani2017attention} predicting $P(w_t
\mid w_{1:t-1})$. This enables Chain-of-Thought reasoning \cite{wei2022chain}, but also drives
hallucination when the model lacks requisite domain knowledge. \textbf{Retrieval-Augmented
Generation (RAG)} \cite{lewis2020rag} mitigates this without updating weights, by retrieving
semantically relevant documents via embedding similarity and concatenating them into the prompt,
reducing hallucination relative to closed-book generation \cite{shuster2021retrieval}.
\textbf{Low-Rank Adaptation (LoRA)} \cite{hu2021lora} instead adapts weights via a low-rank update
$W_{\text{updated}} = W_0 + BA$ ($B \in \mathbb{R}^{d\times r}$, $A \in \mathbb{R}^{r\times k}$, $r
\ll \min(d,k)$), training only $A,B$; \textbf{QLoRA} \cite{dettmers2023qlora} combines this with
4-bit quantization of the frozen base weights, making 32B-scale fine-tuning feasible on commodity
hardware.

\subsection{Related Work}
\label{sec:related}

\textbf{Static analysis} tools (e.g., Slither, SmartCheck) remain the incumbent approach but are
architecturally bound to the EVM and Solidity; porting them to stack-based chains like Algorand or
Solana requires reimplementation, and rule-based analysis struggles with vulnerabilities requiring
contract-specific intent rather than fixed patterns.

\textbf{LLMs for vulnerability detection} have produced hybrid frameworks such as GPTScan
\cite{sun2024gptscan} (LLM reasoning plus static analysis, $>$90\% precision on Solidity) and
multi-agent approaches like LLM-SmartAudit \cite{llmsmartaudit2024}. A recurring finding, echoed by
LLM4Vuln \cite{llm4vuln2024}, is that zero-shot auditing is unreliable whenever security rules are
not well represented in pre-training data -- precisely the condition for PyTeal.

\textbf{Retrieval-augmented vulnerability detection} anchors auditing in retrieved context. Vul-RAG
\cite{vulrag2024} injects historical vulnerability knowledge, reporting 16--24 point accuracy gains
over closed-book prompting; PropertyGPT \cite{propertygpt2025} retrieves formal-property templates,
surfacing 9 of 13 evaluated CVEs. Both adopt a lesson we follow directly: indexing \emph{raw source
code} is suboptimal, since vector similarity over unprocessed code conflates application domain with
security profile; we adopt an analogous \emph{semantic-abstraction} strategy
(Section~\ref{sec:sec_code_desc}).

\textbf{LLM-based security beyond the EVM} remains sparse. The most directly relevant prior study is
our own \cite{boi2025}, which found that PyTeal is markedly harder for LLMs than Rust (a
non-fine-tuned Llama-3 baseline collapses to zero recall on Algorand), that DeepSeek-family models
perform better out of the box but still struggle with AVM-specific nuances, and that a hybrid
prompt-engineering-plus-fine-tuning configuration was necessary for Llama to reach its best Algorand
accuracy (0.65).

%\subsubsection{Research gap addressed by this work}
Two limitations of the state of the art, including our own prior study, 
motivate the present work. First, existing fine-tuning approaches for 
this domain train on a code-to-label mapping that encourages statistical 
pattern memorization -- the model learns \emph{what} a vulnerability signature 
looks like without learning \emph{how} the underlying attack unfolds 
or \emph{why} the absence of a specific check is unsafe, which caps 
generalization to logic vulnerabilities not literally seen in training. 
Second, no prior Algorand-focused study combines fine-tuning with 
retrieval-augmented in-context learning, leaving open whether the two 
techniques are complementary or substitutable, and at which model scale 
each becomes necessary. This paper addresses both gaps through (a) a 
Chain-of-Thought fine-tuning dataset that explicitly supervises the 
reasoning trace, and (b) a semantic-abstraction RAG module integrated 
with, and evaluated jointly against, fine-tuning across both medium-scale 
open models and a SOTA generalist.

\section{Methodology}
\label{sec:methodology}


Figure~\ref{fig:rag_architecture} shows the end-to-end pipeline. The model is invoked twice per
contract: once to generate a syntax-agnostic semantic description used to query the vector store
(Section~\ref{sec:sec_code_desc}), and once to produce the final audit, conditioned on a dynamically
assembled prompt that combines the target code with retrieved context
(Section~\ref{sec:retrieval_workflow}). Fine-tuning (Section~\ref{sec:finetuning_setup}) is designed
so that the same model performs both roles well. The pipeline architecture, task schema, and
training recipe below are instantiated twice -- once against the
Algorand/PyTeal taxonomy of Table~\ref{tab:taxonomy}, once against a seven-class Solana/Rust
taxonomy of Table~\ref{tab:taxonomy_solana}.

\subsection{Vulnerability Knowledge Base}
\label{sec:kb}

For each vulnerability class we curated a structured profile with four information, identical across
languages: a \emph{technical description}, the \emph{attack vector}, the \emph{security check(s)} to
verify, and a \emph{mitigation pattern}. Algorand profiles were cross-validated against Trail of
Bits' documentation \cite{trailofbits_algorand} and \cite{boi2025}; Solana profiles were built
analogously from the Sealevel attacks dataset. 
%Table~\ref{tab:taxonomy} already lists the
%root cause and primary security check for every Algorand class; the knowledge base stores these
%alongside a fuller technical description and a mitigation pattern for each.

This knowledge supplies the ground truth used
to synthesize CoT training targets (Section~\ref{sec:cot_methodology}), and, independently, it
populates the retrieval dataset consumed at inference time by the RAG module
(Section~\ref{sec:rag_implementation}). The same four fields reappear inside the dynamic
checklist injected into the audit prompt (Figure~\ref{fig:checklist_prompt}).

\subsection{Dataset Construction}
\label{sec:dataset_creation}

\subsubsection{Collection and vulnerability injection}
For Algorand, we collected 110 PyTeal contracts (100 training, 10 validation) from Algorand's
official repository \cite{algorand_pyteal_github}, covering DeFi/AMM, escrow, payment, and
governance contracts. We manually injected vulnerabilities into safe templates by removing or
weakening the specific check listed in the corresponding knowledge-base profile, producing pairs
with near-identical business logic but opposite security profiles.

For Solana, we sourced base instruction handlers from real, deployed Rust programs (Solana Program
Library: token-lending, \texttt{spl-governance}, stake-pool, escrow, IDO-pool), so examples 
reflect production Anchor/native programs. Vulnerable variants removed the
specific check for each of the seven classes; some pairs were sourced from
\texttt{coral-xyz/sealevel-attacks} \cite{sealevel_attacks}.

\subsubsection{Composition}
The Algorand training dataset (100 contracts) is 80\% vulnerable (10\% per class) / 20\% safe; the
held-out test set has 45 contracts (5 per class, plus 5 safe). The Solana dataset (267 source pairs)
is instead built as \emph{per-vulnerability contrastive pairs}. The held-out Solana contains 97 contracts.

\subsubsection{Multi-task instruction schema}
\label{sec:training_tasks}
From the base contracts of each language we generated instruction-tuning instances spanning three
tasks (approximately 500 for Algorand, from the 100 base contracts), so that the same underlying
model can serve every stage of the pipeline in Figure~\ref{fig:rag_architecture}:
\begin{description}
\item[Task 1 -- Vulnerability detection.] Generic audit instruction; the target response contains a
\texttt{<think>} step-by-step analysis followed by a \texttt{<final>} verdict. The core
CoT-reasoning task.
\item[Task 2 -- Targeted vulnerability verification.] The instruction names a specific hypothesis,
and the response verifies only that hypothesis. This trains the model as a \emph{hypothesis
verifier}, the same pattern the RAG checklist activates at inference time.
\item[Task 3 -- Semantic code description.] A structured summary of architectural type, functional
intent, and validation logic (checked vs.\ unchecked fields). Outputs are what gets indexed in the
vector store, so consistency between indexing-time and query-time descriptions is critical
(Section~\ref{sec:retrieval_workflow}).
\end{description}

\subsection{Chain-of-Thought Fine-Tuning}
\label{sec:cot_methodology}

Target responses are engineered as a two-phase trace: a \texttt{<think>} phase scanning the contract
handler-by-handler, validating both insecure and secure branches, and a \texttt{<final>} phase
reporting the vulnerability name, cause, and severity. This follows the CoT literature showing
supervised intermediate reasoning improves logic-heavy tasks \cite{wei2022chain}, forcing the model
to state preconditions explicitly before asserting a verdict rather than jumping directly to a
label. Figure~\ref{fig:cot_example} shows a representative training target.

\subsubsection{Data efficiency}
\label{sec:dataset_limitations}
Both the Algorand ($\sim$500 instances from 100 contracts) and Solana (267 pairs) datasets are small relative to typical instruction-tuning datasets.
We follow the "quality-over-quantity" argument of LIMA \cite{zhou2023lima}: each example encodes a 
dense reasoning
trace, so the model learns a transferable \emph{auditing procedure} instead of PyTeal/Rust syntax
from scratch. RAG plays a complementary role: where parametric knowledge from a handful of examples
is incomplete, retrieval supplies the missing rule at inference time. 
%We treat dataset size, especially on Solana, as a limitation (Section~\ref{sec:threats}).

\subsection{Model Selection}
\label{sec:model_selection}

We restrict model selection to the 32B parameter class, excluding smaller ($<$15B) and larger
($>$70B) open models. This is grounded in scaling-law analysis for reasoning \cite{wang2025larger},
reporting a non-monotonic relationship between model size and multi-hop logical-rule inference: both
PyTeal and Solana auditing are high-entropy tasks in this sense, and a preliminary pilot confirmed
14B models lost coherence mid-chain during CoT generation while 32B models (Qwen3-32B, QwQ-32B)
sustained a complete trace. Exploring 70B+ models is left to future work
(Section~\ref{sec:conclusion}).

Within the 32B class we fine-tuned Qwen3-32B \cite{qwen3_2025} and QwQ-32B \cite{qwq32b_2025} for
both languages, since QwQ natively segregates reasoning from answer (aligning with our
\texttt{<think>}/\texttt{<final>} schema) and both show competitive code-intelligence benchmarks.

\subsubsection{Cross-architecture generalization check}
\label{sec:cross_arch_selection}
The two models above share a vendor (Qwen) and a dense architecture; any conclusion drawn only from
them risks being family-specific. We therefore extend the benchmark, for both languages and all four
configurations, with two further generalist models, each adapted with the strategy appropriate to
its own architecture rather than a one-size-fits-all recipe. \textbf{Gemma-4-31B}
\cite{gemma_tech_report} is a dense, 31B-parameter model from a different vendor (Google DeepMind),
adapted with the same full-module LoRA recipe as the other two models
(Section~\ref{sec:finetuning_setup}) -- the cleanest possible cross-family replication.
\textbf{Qwen3-Coder-30B-A3B-Instruct} \cite{qwen3coder_2025} is a mixture-of-experts (MoE) code
model (30.5B total, 3.3B active per token, 128 experts, 8 routed), natively non-thinking, requiring
its own adaptation strategy (Section~\ref{sec:moe_lora}); including it tests whether the recipe's
\emph{qualitative} benefit transfers once a model is adapted on its own architectural terms.

\subsection{Fine-Tuning Configuration}
\label{sec:finetuning_setup}

Qwen3-32B, QwQ-32B, and Gemma-4-31B were fine-tuned with QLoRA \cite{dettmers2023qlora,hu2021lora}
using the Unsloth training framework. The base model was loaded in 4-bit NF4 quantization; LoRA
adapters ($r=64$, $\alpha=128$) were attached to \emph{all} linear projections, including the MLP
modules (\texttt{gate\_proj}, \texttt{up\_proj}, \texttt{down\_proj}) rather than only the attention
projections, which we found necessary to meaningfully affect reasoning behavior rather than surface
style. Full hyperparameters are listed in Table~\ref{tab:hyperparams}.

\subsubsection{Attention-only adaptation for the MoE model}
\label{sec:moe_lora}
Qwen3-Coder-30B-A3B separates each layer's shared attention projections from 128 per-layer expert
feed-forward blocks, routed sparsely (8 active experts per token) by a per-layer router. Targeting
every expert's FFN projections would attach LoRA adapters to 3.37B parameters (9.95\%), but with
only 267--500 training examples and sparse routing, most experts would receive near-zero gradient
signal. We therefore restrict LoRA to the four shared attention projections (53.5M parameters,
0.17\%) -- the architecture-appropriate choice for QLoRA on a sparse MoE model under a small-data
regime, at the cost of leaving the expert feed-forward blocks frozen.
Section~\ref{sec:cross_arch_results} reports how this narrower adaptation performs relative to the
dense models' full-module adaptation.

\subsubsection{Chat template and loss masking}
A custom Jinja2 chat template enforces ChatML-style role boundaries, introduces
\texttt{<think>}/\texttt{<final>} as first-class template constructs, and branches between the CoT
schema (Tasks 1--2) and the direct-answer schema (Task 3). Loss was computed only over response
tokens (\texttt{train\_on\_responses\_only}), masking the fixed instruction/code portion -- focusing
gradient updates on the reasoning trace and verdict, and reducing format-specific overfitting.

\subsubsection{Early stopping}
\label{sec:loss_analysis}
Training and validation loss were logged every 10 steps over 3 epochs (180 steps) for the Algorand
models. Both models converge rapidly over the first 100 steps, with validation loss following the
same trend; beyond step 120--130 a generalization gap opens, more markedly for QwQ-32B, consistent
with its reasoning specialization making it more prone to fitting idiosyncrasies of the small
training set. We fixed training at 3 epochs for both models, stopping at the empirical
validation-loss optimum. Gemma-4-31B and Qwen3-Coder-30B-A3B were fine-tuned under the identical
schedule without a dedicated per-step analysis; both converged without validation loss diverging.

\subsection{Retrieval-Augmented Generation Pipeline}
\label{sec:rag_implementation}

\subsubsection{Knowledge base construction}
The Algorand RAG dataset indexes 40 vulnerable contracts (5 per class); the Solana corpus indexes 38
entries. Each entry stores a vulnerability label, a
semantic description (embedded and searched, Task-3 schema), and a vulnerable snippet (payload,
injected verbatim once retrieved but never embedded). Descriptions were embedded with
\texttt{Qwen3-Embedding-4B} \cite{qwen3_embedding_2025}).

\subsubsection{Semantic-abstraction retrieval}
\label{sec:sec_code_desc}
Indexing raw code risks clustering contracts by \emph{application domain}, the raw-code retrieval 
bias documented for Vul-RAG \cite{vulrag2024}. We instead index
an LLM-generated description constrained by \emph{syntactic abstraction} (omit variable names,
literals, comments) and \emph{security-check mapping} (explicitly enumerate which fields/accounts
are, and are not, validated). This shifts the embedding space toward vulnerability structure, 
increasing the likelihood of surfacing an example sharing the same underlying structure.

\subsubsection{Retrieval and diversification workflow}
\label{sec:retrieval_workflow}
Querying the knowledge base follows a four-phase pipeline (Figure~\ref{fig:rag_architecture}): (1)
the model generates a Task-3 description of the target contract, using the identical schema used at
indexing time; (2) the description is embedded and ranked by cosine similarity against
every entry; (3) rather than taking the top-$N$ candidates by raw score, which risks near-duplicate
vulnerabilities, the pipeline greedily selects distinct vulnerability classes until $N$ are
represented; (4) the snippet and description of each selected candidate are injected as few-shot
context.

\subsubsection{Dynamic checklist prompting}
\label{sec:prompt_engineering}
The prompt enumerates every vulnerability class as an ordered checklist, re-ranked per contract: the
top-$N$ retrieved classes appear first with full technical detail, the rest in abbreviated form so
low-similarity categories are never silently dropped. Showing full detail only for the top-$N$
matches is a context-budget tradeoff against diluting attention.

%fixed a priori from context-budget considerations before any checklist-size ablation had been run;
%for Solana, $N=2$ was determined empirically via a checklist-size ablation.
Section~\ref{sec:ksweep_combined} reports both ablations together; 
the two datasets disagree on the optimal
$k$, underscoring this hyperparameter is data-dependent and should not be assumed transferable
across chains.

\subsection{Fine-Tuning versus SOTA Generalist Models: Rationale}
\label{sec:finetuning_rationale}

In the current landscape, dominated by massive-scale generalist LLMs, the prevailing trend is to
rely on prompt engineering alone, avoiding fine-tuning's cost. This motivates a direct question:
\emph{is it still worth fine-tuning a "small" (32B) model, or do massive generalists render the
practice obsolete?} The generalist approach brings immense parametric knowledge adaptable with no
weight updates, but without domain-specific exposure to an ecosystem's exploit patterns; the
specialist approach starts from weaker raw capacity but is intensively exposed to the audit
procedure via the CoT corpus. Independently of which wins on raw performance, a locally deployable
fine-tuned model retains value for data sovereignty and structural determinism
(Section~\ref{sec:threats}). The benchmark against DeepSeek-V4-Pro in Section~\ref{sec:results}
makes this comparison concrete.

\subsection{Evaluation Metrics}
\label{sec:metrics}
The task is formalized as \emph{multi-label} detection with a single ground-truth label per
contract. Each contract $x$ has exactly one ground-truth label $y(x) \in \mathcal{C} \cup
\{\textsc{safe}\}$, where $\mathcal{C}$ is the taxonomy's $K$ vulnerability classes ($K=8$ for
Algorand, Table~\ref{tab:taxonomy}; $K=7$ for Solana, Table~\ref{tab:taxonomy_solana}). The model's
parsed output for $x$ is a \emph{set} $\hat{Y}(x) \subseteq \mathcal{C}$ (possibly empty, possibly
containing more than one class), since nothing in the prompt or the \texttt{<final>} schema prevents
the model from reporting several findings for one contract. For class $c \in \mathcal{C}$, per-class
counts over the test set $X$ are:
\begin{align}
TP_c &= |\{x \in X : y(x) = c \wedge c \in \hat{Y}(x)\}| \label{eq:tpc}\\
FN_c &= |\{x \in X : y(x) = c \wedge c \notin \hat{Y}(x)\}| \label{eq:fnc}\\
FP_c &= |\{x \in X : c \in \hat{Y}(x) \wedge y(x) \neq c\}| \label{eq:fpc}
\end{align}
Eq.~\eqref{eq:fpc} covers both false-positive cases a reviewer might otherwise conflate: $c$ is
flagged on a \textsc{safe} contract, or $c$ is an \emph{extra} label alongside the correct one on a
vulnerable contract (e.g.\ $\hat{Y}(x) = \{y(x), c\}$) -- both inflate $FP_c$ for class $c$
identically, since both are instances of the model asserting $c$ is present when it is not. $TN$ is
defined only at the aggregate level, over \textsc{safe} contracts predicted empty: $TN = |\{x \in X
: y(x) = \textsc{safe} \wedge \hat{Y}(x) = \emptyset\}|$. We report three complementary aggregates,
all computable from $\{TP_c, FP_c, FN_c\}_{c \in \mathcal{C}}$ and $TN$:
\begin{align}
\text{Accuracy} &= \frac{\sum_c TP_c + TN}{\sum_c TP_c + TN + \sum_c FP_c + \sum_c FN_c}
\label{eq:accuracy}\\
\text{Precision}_{\mu} &= \frac{\sum_c TP_c}{\sum_c TP_c + \sum_c FP_c} \label{eq:precision}\\
\text{Recall}_{\mu} &= \frac{\sum_c TP_c}{\sum_c TP_c + \sum_c FN_c} \label{eq:recall}\\
F_1^{\mu} &=
2\cdot\frac{\text{Precision}_{\mu}\cdot\text{Recall}_{\mu}}{\text{Precision}_{\mu}+\text{Recall}_{\mu}}
\label{eq:f1}\\
F_1^{M} &= \frac{1}{K}\sum_{c \in \mathcal{C}} \frac{2\, TP_c}{2\,TP_c + FP_c + FN_c}
\label{eq:macrof1}
\end{align}
$F_1^{\mu}$ (\emph{micro}-F1, pooling counts across classes before computing the ratio) is the
single number we report as "$F_1$" everywhere in this paper outside
Section~\ref{sec:percategory_formal}, since it weights every contract equally regardless of class
and is the metric this study's RQs are framed around; $F_1^{M}$ (\emph{macro}-F1, averaging each
class's own $F_1$) instead weights every \emph{class} equally, surfacing categories with few
examples that micro-F1 can mask. Section~\ref{sec:percategory_formal} reports both, per class, for
the headline configurations, together with \emph{exact-match accuracy} $|\{x : \hat{Y}(x) =
\{y(x)\}\}|/|X|$ (correct label, and \emph{only} the correct label) -- the strictest per-contract
criterion, since it also penalizes the spurious-extra-label case that $F_1^{\mu}/F_1^{M}$ treat more
leniently as a partial error. In a security-audit context, recall (Eq.~\eqref{eq:recall}) is
arguably the more critical component, since a false negative corresponds to a missed exploitable
bug, whereas low precision mainly costs auditor time ("alert fatigue"); $F_1^{\mu}$
(Eq.~\eqref{eq:f1}), which balances both, is the headline metric used throughout
Section~\ref{sec:results}.

\subsubsection{Impact of Retrieval-Augmented Generation}
\label{sec:rag_impact_analysis}

RAG improves mean F1 in every configuration, through different mechanisms: for base models it
acts as a noise filter, grounding the model in retrieved examples and raising both precision and
recall (Qwen3-32B: from 0.453$\pm$0.082 to 0.735$\pm$0.038 F1); for fine-tuned models,
prior training and retrieved context are complementary, jointly raising QwQ-32B-FT to F1
0.814$\pm$0.014, representing our most stable configuration and best on-premise result; for the SOTA
generalist DeepSeek-V4-Pro, RAG still closes a residual gap, reaching F1 0.918$\pm$0.046.
Three patterns hold across the experiments: (i) RAG is uniformly additive, with every gain larger than its
standard deviation; (ii) fine-tuning and RAG are complementary, not substitutable, demonstrated by QwQ-32B-FT+RAG
(0.814$\pm$0.014), which improves base+RAG (0.784$\pm$0.021); (iii) the SOTA gap narrows but remains for
the 32B-scale models, representing our best on-premise 32B configuration trails DeepSeek-V4-Pro+RAG
(0.918$\pm$0.046) by roughly 10 F1 points, a gap a paired cluster bootstrap confirms as
statistically significant (Section~\ref{sec:bootstrap_ci}).

\finding{1}{On Algorand, for the Qwen family at 32B scale, RAG does not substitute for fine-tuning:
fine-tuned+RAG improves base+RAG by 0.063 F1 for Qwen3-32B and 0.030 F1 for QwQ-32B. Fine-tuning
and RAG are complementary, not interchangeable, for these two models, but this does not hold for
every model at the same parameter scale (Finding 4).}

\finding{2}{The SOTA generalist DeepSeek-V4-Pro reaches high F1 (0.918$\pm$0.046) from retrieval
alone, with no weight update at all. This is not exclusive to a model an order of magnitude larger
than the 32B open-weight models tested here: Finding 4 shows Gemma-4-31B, at the same parameter
scale as Qwen3-32B and QwQ-32B, also closes the gap from RAG alone.}

below the fine-tuned 32B specialist and the SOTA generalist on F1, and both fail for reasons
orthogonal to code understanding, fixed rule coverage for Tealer, an apparent LogicSig-path defect
for Panda, reinforcing this paper's motivation for a semantically-aware, LLM-based approach.

\label{sec:rag_impact_analysis_solana}

observed for the no-RAG comparison (Section~\ref{sec:benchmark_deepseek_solana}).

0.156 F1 (QwQ-32B). Unlike on Algorand,

\subsubsection{Comparison Against an Existing Static-Analysis Tool}
\label{sec:static_tool_comparison_solana}

For Solana, we evaluated the tooling listed in the solsec security-resource index
\cite{solsec}: \texttt{cargo-geiger} only flags \texttt{unsafe} blocks (an unrelated signal), Saber
Vipers is a safe-arithmetic library, L3X is itself LLM-based. We also attempted to include VRust
\cite{vrust2022}, a static analyzer for Solana; on inspection of its released
implementation, however, its account-role checkers (e.g.\ the missing-signer-check rule) key on a
fixed list of variable-name substrings (\texttt{authority}, \texttt{owner}, \texttt{admin},
\texttt{manager}) and a specific interprocedural call pattern mined from the handful of real-world
repositories VRust was validated against, rather than on the account's actual \texttt{is\_signer}
state; a hand-written missing-signer-check violation using this exact naming convention produced
zero findings in our own build of the tool. We therefore exclude VRust from the empirical comparison
rather than report a result its own detection logic is unlikely to make meaningful on this test set.
We did, however, find and successfully run
Radar \cite{radar}, an actively maintained, open-source, template-driven static analyzer for
Anchor/Rust (and Solidity/Stylus) programs, whose built-in rule set covers all seven Solana
categories in this taxonomy (e.g.\ \texttt{missing\_signer\_check}, \texttt{type\_cosplay},
\texttt{missing\_bump\_seed\_canonicalization}). Unlike Tealer and Panda
(Section~\ref{sec:static_tool_comparison_algorand}), Radar operates on raw Rust source via an AST
parser rather than requiring a compiled or crate-complete program, letting it run directly on this
study's unmodified test-set fragments. Table~\ref{tab:radar_comparison} reports its result on the
full 97-contract Solana test set (no RAG, default rule set, single deterministic run).

\subsubsection{CoT-Isolation Ablation}
\label{sec:cot_ablation}

Sections~\ref{sec:impact_finetuning} and~\ref{sec:impact_finetuning_solana} attribute the
base-to-fine-tuned gain to fine-tuning in general, but each language's recipe bundles several
factors that could each explain it on their own: explicit reasoning (CoT) supervision, exposure to
more examples, task breadth, domain-terminology learning, and structured-output-format learning. To
isolate the marginal contribution of CoT supervision specifically, we trained additional
configurations per language that hold the base model, LoRA hyperparameters ($r=64$, $\alpha=128$),
optimizer, schedule, and random seed fixed to those of each language's headline Qwen3-32B
(Config D), varying only the training data and the assistant-response template.

\textbf{Algorand.} The headline recipe (Section~\ref{sec:finetuning_setup}) requires three tasks:
generic detection+reasoning (200 examples), targeted verification (200 examples), and semantic
description (100 examples, no CoT), so three ablations isolate different confounds: \textbf{Config
A} uses the identical 500 examples and three tasks as Config D, but every target is collapsed to the
\texttt{<final>} verdict only -- no \texttt{<think>} trace is ever supervised, isolating task
breadth and example count from CoT supervision. \textbf{Config B} and \textbf{Config C} keep full
\texttt{<think>}+\texttt{<final>} supervision but restrict training to Task 1 only (200 examples)
and Task 2 only (200 examples) respectively, isolating each individual task from the others. All
four configurations are evaluated identically: no RAG, the same 45-contract Algorand test set, mean
$\pm$ std over 5 seeded samples, with per-class metrics computed under the formal protocol of
Section~\ref{sec:metrics}.

Here the result points the other way: removing CoT supervision costs 0.096 Micro-F1, 0.052 Macro-F1,
and 0.066 exact-match, smaller than Algorand's task-breadth effect (0.24--0.30) but not within one
combined standard deviation of Config D, unlike Algorand's A vs. D comparison. Config D's Micro-F1
here (0.419) is computed under the identical formal protocol (Section~\ref{sec:metrics}, $K=7$
scored classes, safe credited only via $TN$ at the aggregate level,
Eq.~\eqref{eq:accuracy}) used for every other Solana headline number in this paper, and is identical
to Table~\ref{tab:rag_comparison_full_solana}'s figure for the same configuration.

\textbf{Synthesis.} CoT supervision's marginal value appears conditional on how
much task breadth the rest of the recipe already supplies. On Algorand, with three tasks and 500
examples, task breadth alone accounts for the fine-tuning gain, and supervising the reasoning trace
on top of it is redundant. On Solana, with a single task and roughly half as many examples,
there is no breadth to substitute for the reasoning signal, and removing it measurably hurts. The Algorand 
gain documented in
Section~\ref{sec:impact_finetuning} is better explained by the multi-task training signal (more
examples, more vulnerability classes, more label/terminology exposure) than by explicit
CoT supervision per se, but this does not generalize unconditionally. Solana's
narrower, single-task recipe shows the reasoning trace retaining real marginal value. This does not
mean the \texttt{<think>} trace is useless on Algorand either, as it still gives the qualitative,
per-transaction reasoning and offers an auditable explanation absent from a verdict-only model,
but the ablation does not support a causal claim
that the trace is what drives Algorand's quantitative F1 improvement, while it does support that
claim for Solana.

\subsubsection{Stability Under Repeated Stochastic Sampling}
\label{sec:rq5_stability}

Every result reported in Sections~\ref{sec:impact_finetuning}--\ref{sec:cross_language} is a mean
over five independently seeded samples per configuration.

\paragraph{Sampling variance}

The mean$\pm$std figures reported throughout this paper (e.g.\
Tables~\ref{tab:rag_comparison_full}--\ref{tab:rag_comparison_full_solana}) are large enough in
several configurations that a single seed could shift the reported F1 by more than the gain
attributed to RAG or fine-tuning alone -- the reason every headline number is reported as mean $\pm$
std rather than a point estimate. Two patterns hold across both languages: RAG reduces
variance as well as raising the mean (lower or equal std in 7 of 8 base/FT-vs.-RAG pairs), and
the best configuration is also the most stable (QwQ-32B-FT+RAG has both the highest mean F1
and the lowest variance on Algorand).

\section{Discussion and Threats to Validity}
\label{sec:threats}

Beyond raw accuracy, the choice between fine-tuning and retrieval carries practical implications
that we discuss here alongside an explicit assessment of the study's limitations, as is appropriate
given the modest scale of the underlying dataset.
Even where a generalist SOTA model matches or exceeds a fine-tuned specialist, fine-tuned 32B models
retain value along two axes: \emph{data sovereignty} (a locally hosted model avoids transmitting
proprietary, pre-deployment contract code to a third-party API) and \emph{structural determinism}
(fine-tuned models internalize the required \texttt{<think>}/\texttt{<final>} output schema more
reliably than prompting alone, easing integration into automated pipelines).

\subsection{Threats to Validity}

\textbf{Dataset scale and statistical power.} The 45-contract test set (5 per class) means
single-digit TP/FP/FN differences cause large metric swings. We report every open-weight
configuration as mean$\pm$std over 5 seeds and as a cluster-bootstrap 95\% CI
(Section~\ref{sec:bootstrap_ci}); the two agree closely. We additionally ran a paired cluster
bootstrap (Section~\ref{sec:paired_bootstrap}) for the comparisons this paper leans on most
heavily against the SOTA generalist, which is what revealed that Gemma-4-31B-FT+RAG's apparent edge
over DeepSeek-V4-Pro+RAG is not statistically significant. We did not extend this paired test to
every pairwise comparison in the study (e.g.\ across the cross-architecture or cross-language
tables), which remains a priority for follow-up work with a larger dataset.

\textbf{Potential pretraining contamination.} The training and RAG dataset derive from Algorand's
public PyTeal repository \cite{algorand_pyteal_github}, plausibly present in the pre-training
dataset of all generalist models evaluated. An 8-gram overlap check against a fresh clone of that
repository found 4 of 45 test contracts (8.9\%, up to 98.7\% overlap) are near-verbatim public
examples -- disproportionately concentrated in the 5-contract safe subset (2 of 5, 40\%). Rather
than only arguing from a per-model score comparison, we recomputed every headline F1 with these 4
contracts excluded (41-contract subset) as a direct sensitivity check: every configuration's F1
\emph{increases} slightly on the decontaminated subset (e.g.\ Qwen3-32B-FT+RAG:
from 0.797 to 0.816; Gemma-4-31B-FT+RAG: from 0.948 to 0.955; DeepSeek-V4-Pro+RAG:
from 0.919 to 0.926), with the sole exceptions of QwQ-32B base and DeepSeek-V4-Pro under no-RAG
prompting, which decrease by $\le$0.006. This rules out the specific concern that memorized
contracts are inflating this paper's headline numbers -- if anything, the flagged contracts are
mildly \emph{harder} for most configurations, not easier -- though it does not establish that the
flagged contracts are unseen by any model's pre-training, only that seeing them does not explain
this paper's results. We have not yet run the overlap check itself against DeepSeek-V4-Pro's
(undisclosed) pre-training dataset, so this remains a doubt on interpretation.

\textbf{Attribution of the fine-tuning gain.} The base-to-fine-tuned improvement reported in
Sections~\ref{sec:impact_finetuning} and~\ref{sec:impact_finetuning_solana} should not be attributed
to CoT supervision specifically; the CoT-isolation ablation in
Section~\ref{sec:cot_ablation} shows this holds only conditionally. On Algorand, removing CoT
supervision while keeping the same data and task breadth (Config A) does not measurably change F1,
while keeping CoT supervision but training on a single task (Configs B, C) costs roughly a quarter
of the F1 score, so the gain is better explained by the breadth and volume of the multi-task
training signal than by the reasoning trace itself. On Solana, whose recipe has no multi-task
structure to substitute for CoT, removing it (Config A) does cost a measurable 0.096 Micro-F1. CoT
supervision's marginal value is therefore conditional on how much task breadth the rest of the
recipe already supplies.

\textbf{LLM response reliability.} Two threats are specific to using an LLM. 
First, \emph{residual non-determinism}: every
reported score is a mean over 5 seeded samples at temperature 0.6 (Section~\ref{sec:rq5_stability}),
which bounds but does not eliminate sampling variance. Second, and more
fundamentally, \emph{chain-of-thought unfaithfulness}: this paper's evaluation, like the fine-tuning
supervision itself, scores only the final \texttt{<final>} verdict, and a correct verdict does not
guarantee that the preceding \texttt{<think>} trace reflects the model's actual decision process
rather than a post-hoc rationalization constructed to match a label the model arrived at some other
way. Prior work on CoT faithfulness \cite{turpin2023faithfulness} shows this gap can be substantial
even when surface-level reasoning looks sound. We did not run a faithfulness-specific probe (e.g.\
deliberately corrupting the reasoning trace and checking whether the verdict changes accordingly);
the qualitative failure patterns discussed throughout this paper are suggestive of genuine
per-transaction tracking, not fabricated post-hoc, but this remains an assumption rather than a
verified property of the fine-tuned models.

\textbf{Other threats.} Ground-truth comparison relies on regex extraction of a fixed vocabulary, a
coarser signal than full human review. The RAG knowledge base and test contracts share the same
source distribution, so performance on out-of-distribution contract styles is untested. The SOTA
comparison relies on one API-served model at one point in time, subject to silent version drift.

\textbf{Architecture-appropriate adaptation.} Section~\ref{sec:cross_arch_results} adapts each model
with the strategy appropriate to its own architecture (full-module LoRA for dense Gemma-4-31B,
attention-only for sparse-MoE Qwen3-Coder-30B-A3B, Section~\ref{sec:moe_lora}) rather than holding
adaptation method fixed, since the latter would mean deliberately mis-adapting one model.
Consequently, we cannot attribute Qwen3-Coder-30B-A3B's weaker Solana results uniquely to the MoE
paradigm versus the smaller effective capacity its adaptation reaches.

None of these threats invalidate the qualitative trends in Section~\ref{sec:results}, which are
consistent across four model families, but they bound how precisely the point estimates should be
read.

\subsection{Limitations}
\label{sec:limitations}
Independent of the validity threats above, the proposed architecture has three structural
limitations. First, RAG effectiveness is bounded by knowledge-base coverage: for a genuine zero-day
pattern absent from the vector store, the system loses its factual anchor and falls back on
parametric knowledge alone. Second, retrieval based exclusively on natural-language descriptions
inherits any imprecision, omission, or ambiguity in the LLM-generated description itself, which can
misdirect retrieval toward irrelevant context. Third, the current pipeline analyzes each contract in
isolation and does not trace state or authority flows across multiple interdependent contracts, so
cross-contract vulnerabilities fall outside its current scope.

\section{Conclusion and Future Work}
\label{sec:conclusion}

This paper presented a hybrid, LLM-centric pipeline for vulnerability detection in low-resource
smart-contract languages, combining Chain-of-Thought fine-tuning with a semantic-abstraction RAG
module, evaluated on Algorand/PyTeal and independently replicated on Solana/Rust, across four
open-weight model families and a SOTA generalist benchmark, with every result reported as mean $\pm$
std over 5 seeded samples.

The central finding is that retrieval over semantic descriptions is the pipeline's dominant and most
reliable lever, while fine-tuning's necessity on top of it depends on \emph{which model} is being
adapted, not cleanly on parameter scale (Section~\ref{sec:cross_arch_results}). Across all four
model families and both languages, RAG raises F1 in every configuration tested; fine-tuning's
incremental contribution once RAG is already present does not show the same consistency. For
Qwen3-32B and QwQ-32B, the models on which this pipeline was originally developed, fine-tuning and
RAG are complementary at 32B scale: neither alone reaches the best configuration's F1, and the SOTA
generalist DeepSeek-V4-Pro (0.918$\pm$0.046, retrieval alone, no weight update) remains the ceiling
on Algorand. This does not generalize to every model at the same scale: Gemma-4-31B, a dense model
at the same 32B scale, closes the domain gap on Algorand from RAG alone, with fine-tuning adding a
statistically null $+0.004$ F1 on top of it (Section~\ref{sec:cross_arch_results}); on Solana, both
Gemma-4-31B and Qwen3-Coder-30B-A3B show a statistically null fine-tuning contribution once RAG is
present. \emph{How much} fine-tuning can add, where it does add something, is bounded by how much of
a model's capacity the intervention actually reaches -- Gemma-4-31B's full-module LoRA sets this
study's highest F1 point estimate (0.948, Algorand), statistically indistinguishable from the SOTA
generalist (Section~\ref{sec:bootstrap_ci}), while Qwen3-Coder-30B-A3B's necessarily narrower
attention-only LoRA reaches a visibly lower ceiling, especially on Solana -- but \emph{whether} it
adds anything measurable once RAG is already present is not predicted by scale alone. The
CoT-isolation ablation (Section~\ref{sec:cot_ablation}) further narrows what, within fine-tuning,
actually drives the gain where one exists: on Algorand, it is multi-task breadth and example volume,
not the Chain-of-Thought reasoning trace itself, which contributes no measurable gain once breadth
is held fixed. These findings refine our earlier conclusion \cite{boi2025} that fine-tuning alone
closes the gap to a much larger generalist: for the models and languages where fine-tuning does add
value on top of RAG, it narrows the gap substantially for organizations restricted to on-premise,
medium-scale models; for others (Gemma-4-31B on Algorand, and both Gemma-4-31B and
Qwen3-Coder-30B-A3B on Solana), RAG on an appropriately chosen base model already gets there without
any fine-tuning at all. Both results hold only on contracts within the single-vulnerability,
single-contract analysis scope this study evaluates (Section~\ref{sec:limitations}); we make no
claim about multi-vulnerability or cross-contract settings, which this pipeline has not been tested
on.

Future work should address Section~\ref{sec:threats}'s threats through a larger,
decontamination-audited benchmark with paired significance testing. Architecturally, three
directions stand out: an \emph{agentic} workflow where the model iteratively invokes tools (static
analyzers, the native compiler, the RAG index itself) rather than receiving a fixed context bundle;
a \emph{hybrid semantic-structural} retrieval representation indexing generalized code abstractions
alongside text descriptions, in the spirit of Vul-RAG \cite{vulrag2024} and PropertyGPT
\cite{propertygpt2025}; and extending analysis from single-contract to \emph{cross-contract}
reasoning across interdependent Algorand applications.
